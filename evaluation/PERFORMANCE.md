# 性能優先の開発

まず検索品質を維持したまま遅い検索を改善する。資料セット追加はいったん保留する。

## 初回の改善（2026-11-18）

公式ドキュメント502ページ、固定20問と短い語・一致しない語など7問を合わせた27問を各15回、合計405回検索した。旧実装 `969da92` と新実装を、同じ本文・タイトル・URLの集合で比較した。

| 指標 | 改善前 | 改善後 |
| --- | ---: | ---: |
| p50 | 3.584ms | 3.111ms |
| p95 | 40.255ms | 6.822ms |
| p99 | 47.182ms | 10.174ms |
| 固定20問の上位5件成功数 | 20 | 20 |

p95で約5.9倍。27問の総件数と上位10件のURL・順序がすべて一致した。本文・タイトル・URLから計算したSHA-256で同じコーパスであることを確認した。

## 変更

- 1文字・2文字の文字列に専用の転置索引を追加し、本文全走査を避ける。
- 3文字以上の語は既存のtrigram索引を使い、混在検索では候補の集合を一度だけ交差する。候補1件ごとにFTS検索をやり直す実行計画を避ける。
- 順位を決めてから上位結果の本文を取得する。件数・順位・本文は同じ読み取りトランザクションで扱う。
- 登録・更新・削除時に専用索引も同じトランザクションで更新する。旧DBは起動時に既存本文から構築するため、再クロールは不要。

検索結果のキャッシュは使っていない。短い語は従来どおり部分一致、長い語は混在時もFTSの大文字小文字処理に統一した。ASCII以外の大文字小文字について、以前の混在検索のSQLite部分一致と結果が変わる場合がある。

## 費用と測定範囲

この実行環境で専用索引の構築は約4.8秒。実験DBの物理サイズは約52.4MBから64.5MBへ増えた。再構築による空きページも含む物理サイズで、必要最小サイズの測定ではない。登録時の索引生成コストも増える。メモリ使用量・大量更新の性能は未測定。

検索は逐次実行で、各問1回のウォームアップ後に測定する。毎回SQLite接続を開くが、OSやSQLiteの読み込みキャッシュは温まった状態。HTTP通信・画面描画・同時アクセス・起動時の索引構築を検索時間には含めない。実サイトや他の検索エンジンとの速度比較ではない。

## 再測定

```sh
# 初回はアプリ起動で専用索引を自動構築する
python app.py
# アプリを停止し、収集も止まった状態で測定する
python benchmark.py --rounds 15 --output evaluation/local-performance.json
```

旧実装での再現には、別のcheckout/worktreeを `969da92` に固定し、今回の `benchmark.py` をそのルートへコピーする。`--db` には同じ現在のDBを指定する。旧実装は専用索引を参照しない。比較前後でDBへの書き込みを行わず、`corpus_sha256` と問の集合、回数を確認する。DBファイルそのもののハッシュは索引追加だけでも変わるため、コーパス識別とは分けている。
