# 性能優先の開発

まず検索品質を維持したまま遅い検索を改善する。資料セット追加はいったん保留する。

## 初回の改善（2026-11-18）

公式ドキュメント502ページ、固定20問と短い語・一致しない語など7問を合わせた27問を各15回、合計405回検索した。旧実装 `969da92` と新実装を、同じ本文・タイトル・URLの集合で比較した。

| 指標 | 改善前 | 改善後 |
| --- | ---: | ---: |
| p50 | 3.584ms | 3.111ms |
| p95 | 40.255ms | 6.822ms |
| p99 | 47.182ms | 10.174ms |
| 固定20問の上位5件成功数 | 20 | 20 |

p95で約5.9倍。27問の総件数と上位10件のURL・順序がすべて一致した。本文・タイトル・URLから計算したSHA-256で同じコーパスであることを確認した。

- [改善前の生データ](performance-before.json)
- [改善後の生データ](performance-after.json)
- [比較・費用の記録](performance-comparison.json)

## 変更

- 1文字・2文字の文字列に専用の転置索引を追加し、本文全走査を避ける。
- 3文字以上の語は既存のtrigram索引を使い、混在検索では候補の集合を一度だけ交差する。候補1件ごとにFTS検索をやり直す実行計画を避ける。
- 順位を決めてから上位結果の本文を取得する。件数・順位・本文は同じ読み取りトランザクションで扱う。
- 登録・更新・削除時に専用索引も同じトランザクションで更新する。旧DBは起動時に既存本文から構築するため、再クロールは不要。

検索結果のキャッシュは使っていない。短い語は従来どおり部分一致、長い語は混在時もFTSの大文字小文字処理に統一した。ASCII以外の大文字小文字について、以前の混在検索のSQLite部分一致と結果が変わる場合がある。

## 費用と測定範囲

この実行環境で専用索引の構築は約4.8秒。実験DBの物理サイズは約52.4MBから64.5MBへ増えた。再構築による空きページも含む物理サイズで、必要最小サイズの測定ではない。登録時の索引生成コストも増える。メモリ使用量・大量更新の性能は未測定。

検索は逐次実行で、各問1回のウォームアップ後に測定する。毎回SQLite接続を開くが、OSやSQLiteの読み込みキャッシュは温まった状態。HTTP通信・画面描画・同時アクセス・起動時の索引構築を検索時間には含めない。実サイトや他の検索エンジンとの速度比較ではない。

## 再測定

```sh
# 初回はアプリ起動で専用索引を自動構築する
python app.py
# アプリを停止し、収集も止まった状態で測定する
python benchmark.py --rounds 15 --output evaluation/local-performance.json
```

旧実装での再現には、別のcheckout/worktreeを `969da92` に固定し、今回の `benchmark.py` をそのルートへコピーする。`--db` には同じ現在のDBを指定する。旧実装は専用索引を参照しない。比較前後でDBへの書き込みを行わず、`corpus_sha256` と問の集合、回数を確認する。DBファイルそのもののハッシュは索引追加だけでも変わるため、コーパス識別とは分けている。

## 1万ページ・8並列の検索API（2026-11-18）

ローカルの検索APIに8クライアントから、27種類の検索を計432回実行した。索引は実際の公式ドキュメント502ページと、本文の長さを変えた抜粋9,498件で構成した。リクエストごとにHTTP接続を開き、本文の受信までを測定した。各検索を1回ウォームアップしてから測定し、検索結果キャッシュは使っていない。

| 指標 | 改善前 | 改善後 |
| --- | ---: | ---: |
| p50 | 123.4ms | 19.3ms |
| p95 | 475.9ms | 33.1ms |
| p99 | 649.8ms | 38.5ms |
| 毎秒リクエスト数 | 50.1 | 398.6 |

この負荷でp95 50ms以内を達成した。27種類すべてでHTTP応答本文のハッシュが一致した。結果はこの環境・コーパスでの性能を示す。実ドキュメント1万ページでの負荷と品質は未測定。[測定データ](performance-http-10k.json)

タイトルの単語を索引更新時に正規化し、検索時の順位計算とホスト照合をSQLite内で行う。短い語の検索では本文を含む索引から候補のタイトルを読み出す処理も省いた。SQLiteの読み取り時は最大256MiBのメモリマップを要求する。既存DBの起動時には保存済みデータからタイトル用のテーブルを作成する。

```sh
python benchmark_http.py --db search.db --build /tmp/little-search-10k.db --output /tmp/search-http.json
python benchmark_http.py --db /tmp/little-search-10k.db --output /tmp/search-http-repeat.json
```

初回は未使用の出力パスを指定する。元DBは読み取り専用で開き、作業用DBに複製する。測定中の外部サイトへの通信はない。改善前の実装で比較する場合は、別のcheckoutを `4459c15` に固定して今回の `benchmark_http.py` をコピーし、作成済みの同じDBに対して2行目を実行する。

## ページ更新中の検索API（2026-11-18）

同じ1万ページに8クライアントから計1,080回検索した。同時に1スレッドで毎秒最大20件のペースで保存済みページを書き直した。既存の本文とタイトルを使うため、実際の索引書き込みを行いながら、検索の応答を実行前と比較できる。

| 指標 | 改善前（DELETE） | 改善前（WAL） | 改善後（WAL） |
| --- | ---: | ---: | ---: |
| 検索APIのp95 | 45.2ms | 37.9ms | 31.7ms |
| 検索APIのp99 | 57.6ms | 50.5ms | 39.3ms |
| ページ更新のp95 | 122.2ms | 122.9ms | 32.4ms |
| 測定中に開始し、完了した更新 | 30 | 30 | 54 |

全27種類で応答本文が一致した。通常起動時にWALを有効にして、読み取り中にも更新を確定できるようにした。更新・削除時はURLの索引から対象行を見つけ、本文と各検索索引を同じトランザクションで更新する。測定対象にはHTTP通信と索引更新を含み、ページを外部サイトから取得する時間は含まない。[測定データ](performance-http-refresh.json)

```sh
python benchmark_http.py --db /tmp/little-search-10k.db --rounds 40 --refresh-hz 20 --output /tmp/search-refresh.json
```

更新負荷は一時コピーに対して実行し、指定したDBはそのまま残る。`--journal delete` を指定すると一時コピーをロールバックジャーナル方式で測定できる。

## 10万ページ・8並列の検索API（2026-11-18）

実資料502ページと負荷試験用の抜粋99,498件を索引に登録し、27種類の検索を各12回実行した。ローカルHTTPで8並列、初回ウォームアップ後、ページ更新なしで測った。

| 指標 | 改善前 | 改善後 |
| --- | ---: | ---: |
| p50 | 68.6ms | 52.2ms |
| p95 | 211.2ms | 143.4ms |
| p99 | 269.5ms | 229.2ms |
| 毎秒リクエスト数 | 96.0 | 121.7 |

測定順を逆にして再測定したときのp95は195.8msから142.8ms。全4回で検索結果の件数・順位・抜粋を含むHTTP応答が、27種類すべてで一致した。前の1万ページでの目標だったp95 50msを、この10万ページ条件では超えている。[測定データ](performance-http-100k.json)

サイト指定のない短い語の検索では、タイトルの行を読む前に索引から直接件数を数える。長い語の検索では、タイトル内に検索語が順番どおり並ぶ候補で1ページ目が埋まるときに限り、そのグループ内で関連度を計算する。候補が足りない場合や2ページ目以降は全候補を順位付けする。読み取り時にSQLiteへ要求するメモリマップ上限は約2GiBに広げた。マップされたファイルのページはOSが必要に応じて読み込む。

```sh
python benchmark_http.py --db search.db --build /tmp/little-search-100k.db --pages 100000 --rounds 12 --output /tmp/search-100k.json
python benchmark_http.py --db /tmp/little-search-100k.db --rounds 12 --output /tmp/search-100k-repeat.json
```

旧版は `1e71f39` のcheckoutで、作成済みの同じDBを指定して2行目を実行する。
