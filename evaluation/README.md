# v0.1の目標

よく読む技術サイトを横断して、欲しい情報をすぐ見つけられる個人用検索エンジン。

対象候補はPython・SQLite・MDN・PostgreSQL・Gitの公式ドキュメント。`cases.json` に各サイト4問ずつ、実際の調べ物・検索語・期待するURLを固定する。URLは取得前の候補であり、robots.txt・リダイレクト・ページ変更によって見直す。

## 合格基準

- 5サイト・合計500ページを保存できる
- 固定20問の16問以上で期待ページが上位5件に入る
- 500ページ以上の索引で各検索の所要時間が1秒未満
- 保存したサイトをまとめて更新し、失敗ページを再取得できる

## 測定

```sh
python evaluate.py --collect --output evaluation/local-report.json
python evaluate.py --output evaluation/local-report.json
```

`--collect` は公開サイトへ通信し、まず評価対象20ページを1ページずつ取得する。全500ページを集めるコマンドではない。通常はアプリ停止中に実行する。既存の本文・索引は更新するが、削除しない。

未登録の期待ページは `covered: false` として表示し、20問全体の成功数では不合格として数える。検索語だけから結果を作ったり、期待URLをランキングに使ったりしない。検索時間は各問3回の中央値で、API通信やブラウザー描画は含まない。500ページ未満の計測を速度目標の達成とは扱わない。

## 500ページの収集

```sh
python collect.py
python evaluate.py --output evaluation/local-report.json
```

アプリを停止して実行する。各公式ホストの合計100ページを目指し、最大5サイトを並行収集する。同じホストへのリクエストは最低1秒、robots.txtにcrawl-delayがあればそれ以上あける。Pythonは `/ja/3/`、SQLiteは同一ホスト内、MDNは `/ja/docs/Web`、PostgreSQLは `/docs/current/`、Gitは `/docs` に限定する。クエリ付きURLとPDF等は対象外。

収集候補と成功・スキップ・失敗をDBの `frontier` テーブルへ保存する。同じコマンドを再実行すると未処理候補から再開する。失敗したURLだけ試し直す場合は `python collect.py --retry-failed`。件数目標に達していても試行し、新しいリンクの収集は行わない。実行中の強制終了で残った処理も次回再開する。CLI収集はアプリ画面の停止ボタンとは連動しない。複数の収集プロセスを同時に起動しない。

1回につき各サイト最大500URLを試行し、候補は各3000件まで保持する。ページ数が100に達したサイトは終了する。`--target`（各サイト1〜500ページ）、`--budget`（各サイト1〜1000試行）で上限を変更できる。robots拒否や候補不足があれば目標未達のまま終了するので件数を確認する。

評価レポートの `sites` にホスト別件数を表示し、対象5ホストがそれぞれ100ページ以上なら `corpus_pass` がtrueになる。

## 次の作業

1. 評価対象ページを取得し、URL変更や取得失敗を確認する
2. 5サイトの収集範囲と上限を設定し、500ページで測定する
3. 上位5件に入らない問の本文抽出・ランキングを改善する
4. サイト単位の更新と失敗ページの再取得を実装する（対応済み）

画面のクローラーは1回最大30ページ。500ページ収集用CLIは別に用意した。500ページでの検索品質と一括更新の検証結果は以下に記載する。CIのテスト成功とv0.1の合格は区別する。

## 初回測定（2026-11-15）

[測定結果](baseline.json)：19ページを保存。MDN CORSのURL移転を確認して期待URLを修正した結果、20問中19問で上位5件に入った。SQLite SELECTのページは2MB上限で取得できなかった。19ページだけの小さな索引での結果なので、500ページでの検索品質・速度の達成は引き続き未検証。

## 500ページ測定（2026-11-16）

[測定結果](corpus-500.json)：5サイト各100ページ、合計500ページで固定20問中18問が上位5件に入った。各問3回の検索時間の中央値で、最も遅い問は約26.1ms。規模・検索品質（16/20以上）・ローカル検索速度の基準を通過した。API通信・画面描画の時間は含まない。

残った検索課題は、SQLite SELECTの本文が2MB上限で未取得であることと、`git log` の期待ページが上位5件から外れたこと。収集中にはPostgreSQLの1ページでHTTP 503が発生し、失敗URLとして保存した。小規模測定から検索語や期待URLを変えずに計測している。

サイト単位の一括更新と失敗ページの再取得を追加した。上記2問の改善結果は以下に記載する。


## 更新・再取得の確認（2026-11-16）

画面からサイト単位の保存済みURL更新と失敗URLのみの再取得ができる。成功・失敗はクロール履歴へ記録し、更新失敗時は古い本文を残す。再取得成功時は失敗一覧とCLI収集の失敗状態を解除する。

前回の収集でHTTP 503だったPostgreSQLの `monitoring.html` は、実際に再取得して成功した。一括更新・失敗時の本文保持・再取得による失敗解除は一時DBとブラウザーでも確認している。

[実サイトでの更新確認](refresh-smoke.json)：Python公式ドキュメントの保存済み100ページを一括更新し、100ページすべて成功。PostgreSQLの失敗ページ再取得後は合計501ページ。これで最初に決めた規模・検索品質・速度・更新運用の基準を一通り確認できた。検索時間の数値はローカル環境依存で、継続的な運用や自然文検索の品質を保証するものではない。


## 取得・ランキング改善（2026-11-17）

[再測定結果](ranking-improvement.json)：502ページ、固定20問中20問が上位5件。SQLite SELECTとgit logはともに1位になった。各問3回の中央値で最大約58.2ms。検索語と期待URLは前回から変えていない。

SQLite SELECTのHTMLは2,033,807バイトだったため、取得上限を2MBから4MBへ拡大した。上限超過時の拒否は継続する。git logではタイトルの `git-log` を単語に区切り、問い合わせとの単語一致率と語順一致を優先する。単語全体で照合するため、`log` と `logging` は区別する。2文字以下の語を含む検索にも同じタイトル評価を適用し、これまでのURL順のみの並びを改善した。

これは固定の小さな評価セットを使って改善した結果であり、未知の検索語や自然文検索への汎化性能は未測定。以前のレポートは比較用に残す。
